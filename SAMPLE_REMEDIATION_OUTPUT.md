## Vulnerability #1: SQL Injection

# SQL Injection Remediation

**Vulnerability:** SQL Injection in user login form
**Severity:** critical
**File:** vulnerabilities/sqli/source/low.php
**Line:** 15

## Current Code (Vulnerable)

```php
$query = "SELECT * FROM users WHERE user_id = '" . $_GET['id'] . "';";
$result = mysqli_query($GLOBALS["___mysqli_ston"], $query);
```

## Recommended Fix

```php
// Use prepared statements instead of string concatenation
$stmt = $mysqli->prepare("SELECT * FROM users WHERE id = ?");
$stmt->bind_param("i", $id);
$stmt->execute();
$result = $stmt->get_result();
```

## Explanation

User input is concatenated directly into SQL query without sanitization, allowing attackers to modify the SQL statement structure.

**Why this works:**
- Prepared statements separate SQL logic from data
- User input is treated as data, not executable code
- Database engine handles proper escaping automatically

## Additional Recommendations

1. **Input Validation:** Validate and sanitize all user inputs
2. **Least Privilege:** Use database accounts with minimal permissions
3. **WAF:** Consider using Web Application Firewall rules
4. **Monitoring:** Log and monitor for SQL injection attempts

## References

- OWASP SQL Injection Prevention Cheat Sheet
- CWE-89: Improper Neutralization of Special Elements used in an SQL Command
- OWASP Top 10 - A03:2021 Injection

## Vulnerability #2: Cross-Site Scripting (XSS)

# Cross-Site Scripting (XSS) Remediation

**Vulnerability:** Reflected XSS in search functionality
**Severity:** high
**File:** vulnerabilities/xss_r/source/low.php
**Line:** 8

## Current Code (Vulnerable)

```php
echo "<pre>Hello " . $_GET['name'] . "</pre>";
```

## Recommended Fix

```php
// Use htmlspecialchars() to encode output
echo "Hello " . htmlspecialchars($name, ENT_QUOTES, 'UTF-8');

// For HTML attributes
echo '<input value="' . htmlspecialchars($value, ENT_QUOTES, 'UTF-8') . '">';

// For JavaScript context
echo '<script>var name = ' . json_encode($name) . ';</script>';
```

## Explanation

User input reflected in HTML output without encoding, allowing attackers to inject malicious scripts.

**Why this works:**
- HTML encoding converts special characters to entities
- Browser renders entities as text, not executable code
- Prevents script injection in HTML context

## Context-Specific Encoding

| Context | Encoding Method |
|---------|----------------|
| HTML Body | `htmlspecialchars()` or `escape()` |
| HTML Attribute | `htmlspecialchars()` with ENT_QUOTES |
| JavaScript | `json_encode()` or JSON.stringify() |
| URL | `urlencode()` or `urllib.parse.quote()` |
| CSS | CSS encoding or avoid dynamic CSS |

## Additional Recommendations

1. **Content Security Policy:** Implement CSP headers
2. **HTTPOnly Cookies:** Prevent cookie theft via XSS
3. **Input Validation:** Validate input format and type
4. **Output Encoding:** Always encode based on context

## References

- OWASP XSS Prevention Cheat Sheet
- CWE-79: Improper Neutralization of Input During Web Page Generation
- OWASP Top 10 - A03:2021 Injection

## Vulnerability #3: OS Command Injection

# Command Injection Remediation

**Vulnerability:** OS Command Injection in ping functionality
**Severity:** critical
**File:** vulnerabilities/exec/source/low.php
**Line:** 12

## Current Code (Vulnerable)

```php
$output = shell_exec("ping -c 4 " . $_GET['ip']);
echo "<pre>" . $output . "</pre>";
```

## Recommended Fix

```php
// AVOID: Using shell_exec, exec, system with user input
// shell_exec("ping " . $ip);  // VULNERABLE

// BETTER: Use escapeshellarg() if shell is necessary
$ip = escapeshellarg($ip);
$output = shell_exec("ping -c 4 " . $ip);

// BEST: Avoid shell entirely, use native functions
// For ping, use socket functions or external library
// For file operations, use PHP file functions
```

## Explanation

User input passed to shell command without validation, allowing attackers to execute arbitrary system commands.

**Why this works:**
- Argument lists prevent shell interpretation
- No shell metacharacters are processed
- Commands and arguments are separated explicitly

## Shell Metacharacters to Block

```
; | & $ ` \ ! > < ( ) [ ] { } * ? ~ # ^ " '
```

## Additional Recommendations

1. **Whitelist Validation:** Only allow expected input patterns
2. **Avoid Shell:** Use language-native functions instead
3. **Least Privilege:** Run with minimal system permissions
4. **Sandboxing:** Use containers or restricted environments

## Safe Alternatives

| Dangerous Function | Safe Alternative |
|-------------------|------------------|
| `shell_exec()` | Native PHP functions |
| `exec()` | Parameterized execution |
| `system()` | Library functions |
| `os.system()` | `subprocess.run()` with list |
| `eval()` | Never use with user input |

## References

- OWASP Command Injection Prevention Cheat Sheet
- CWE-78: OS Command Injection
- OWASP Top 10 - A03:2021 Injection

## Vulnerability #4: Path Traversal

# Path Traversal Remediation

**Vulnerability:** Local File Inclusion via path traversal
**Severity:** high
**File:** vulnerabilities/fi/source/low.php
**Line:** 6

## Current Code (Vulnerable)

```php
$file = $_GET['page'];
include($file);
```

## Recommended Fix

```php
// Use whitelist approach
$allowed_files = ['home.php', 'about.php', 'contact.php'];
$page = $_GET['page'] ?? 'home.php';

if (in_array($page, $allowed_files)) {
    include($page);
} else {
    // Handle error
    include('404.php');
}

// OR use basename() and realpath() validation
$base_dir = '/var/www/html/pages/';
$file = basename($_GET['page']);
$full_path = realpath($base_dir . $file);

// Ensure path is within allowed directory
if ($full_path && strpos($full_path, $base_dir) === 0) {
    include($full_path);
}
```

## Explanation

Direct file inclusion with user input allows attackers to access arbitrary files on the system using `../` sequences.

**Why this works:**
- Whitelist restricts files to known-safe set
- `realpath()` resolves `../` sequences
- Path validation ensures files stay in allowed directory

## Dangerous Patterns

```
../../../etc/passwd
..\..\..\..\windows\system32\config\sam
....//....//etc/passwd
%2e%2e%2f%2e%2e%2f
```

## Additional Recommendations

1. **Whitelist Only:** Never use blacklist for path validation
2. **No Direct User Input:** Map user input to safe filenames
3. **Chroot Jails:** Use restricted filesystem views
4. **Access Controls:** Implement proper file permissions

## Validation Steps

1. Normalize path (resolve `../`)
2. Convert to absolute path
3. Verify prefix matches allowed directory
4. Check file exists and is readable
5. Verify file type if applicable

## References

- OWASP Path Traversal Prevention Cheat Sheet
- CWE-22: Improper Limitation of a Pathname to a Restricted Directory
- OWASP Top 10 - A01:2021 Broken Access Control

## Vulnerability #5: Hardcoded Credentials

# Hardcoded Credentials Remediation

**Vulnerability:** Database password hardcoded in source code
**Severity:** high
**File:** config/config.inc.php
**Line:** 8

## Current Code (Vulnerable)

```php
$_DVWA['db_password'] = 'p@ssw0rd';
$_DVWA['db_user'] = 'dvwa';
```

## Recommended Fix

```php
// Use environment variables
$db_password = getenv('DB_PASSWORD');

// OR use configuration file (outside web root)
$config = parse_ini_file('/etc/myapp/config.ini');
$db_password = $config['db_password'];

// Connection example
$mysqli = new mysqli(
    getenv('DB_HOST'),
    getenv('DB_USER'),
    getenv('DB_PASSWORD'),
    getenv('DB_NAME')
);
```

## Environment Configuration

Create `.env` file (add to `.gitignore`):
```bash
DB_PASSWORD=your_secure_password_here
API_KEY=your_api_key_here
SECRET_KEY=your_secret_key_here
```

Docker deployment:
```yaml
services:
  app:
    environment:
      - DB_PASSWORD=${DB_PASSWORD}
      - API_KEY=${API_KEY}
    env_file:
      - .env
```

## Explanation

Credentials stored in source code are exposed in version control, logs, and accessible to anyone with code access.

**Why this works:**
- Credentials stored outside source code
- Different values per environment (dev/staging/prod)
- Secrets not committed to version control
- Easier credential rotation

## Additional Recommendations

1. **Secrets Management:** Use dedicated secrets manager in production
2. **Rotation Policy:** Regularly rotate credentials
3. **Access Control:** Limit who can access secrets
4. **Encryption:** Encrypt secrets at rest and in transit
5. **Audit Logging:** Log secret access and changes

| Azure | Azure Key Vault |
| GCP | Google Secret Manager |
